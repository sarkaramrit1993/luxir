# aarch64 Port Implementation Plan (rev 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make luxir configure, compile, test and pass ASan on native arm64 Linux, from one Dockerfile that serves both amd64 and arm64, without changing any x86-64 behavior.

**Architecture:** One `.devcontainer/Dockerfile` gated on Docker's built-in `TARGETARCH`. Both architectures converge on the same filesystem contract (`/opt/gcc/bin`, `/opt/cmake/bin`, `/opt/vcpkg/installed`), so every stage after the toolchain stage is arch-agnostic apart from one triplet name. Tasks are ordered so the arm64 container exists **before** any source change, giving every source fix real aarch64 GCC feedback instead of a proxy check on the macOS host.

**Tech Stack:** C++26, GCC 16, CMake 4.4.3 + presets v6, Ninja, vcpkg (manifest off, overlay triplets), gtest, google-benchmark, Docker buildx.

**Spec:** This plan is its own spec. It supersedes rev 1 entirely and supersedes the prior session's `LUXIR-NOTES.md` (untracked) wherever they disagree.

## As shipped (read before reusing any step)

This plan is kept as the record of intent. Where it and the branch disagree, the branch wins. Known differences:

- **Task 2:** the code block pins `DYNAMIC_LIST` via `LUXIR_OPENBLAS_EXTRA`. Nothing in Phase A depends on the source tree. `.devcontainer/Dockerfile.dockerignore` excludes everything except `.devcontainer/` and four `deps/` paths, so the image builds without `src/`, `test/`, `CMakeLists.txt` or `CMakePresets.json`.

### Task 1: Fix the committed arm64 triplet architecture token

`deps/triplets/common/linux-aarch64.cmake:2` sets `VCPKG_TARGET_ARCHITECTURE aarch64`. vcpkg does not accept that token. In `scripts/toolchains/linux.cmake` at the pinned baseline `a1cae005`, the accepted values are `x64`, `x86`, `arm`, `arm64`, `riscv64`, and the mapping runs the other way:

```cmake
elseif(VCPKG_TARGET_ARCHITECTURE STREQUAL "arm64")
    set(CMAKE_SYSTEM_PROCESSOR aarch64 CACHE STRING "")
```

`arm64` is the triplet value; `aarch64` is what vcpkg derives from it. With `aarch64` no branch matches, so `CMAKE_SYSTEM_PROCESSOR` stays **empty**. The cross-compile block further down that file is itself guarded on `AND CMAKE_SYSTEM_PROCESSOR`, so it does not run either, and `CMAKE_CROSSCOMPILING` is left at CMake's default of TRUE because the toolchain sets `CMAKE_SYSTEM_NAME`. The damage is mostly silent rather than loud:

- OpenBLAS derives its `ARM64` variable from `CMAKE_SYSTEM_PROCESSOR`, so `DYNAMIC_CORE` comes out empty and `cmake/arch.cmake` prints "DYNAMIC_ARCH is not supported on this architecture, removing from options" -- **dropping a requested feature without failing**.
- FAISS branches on `CMAKE_SYSTEM_PROCESSOR MATCHES "(aarch64|arm64|ARM64)"`, which never fires.
- vcpkg-tool's platform expressions compare the literal, so both `arm` and `arm64` evaluate false and every port's arm64 handling is skipped.

### Task 2: Stop pinning an x86 OpenBLAS core on arm64

`deps/ports/openblas/portfile.cmake` passes `-DTARGET=NEHALEM` unconditionally inside `vcpkg_cmake_configure`. NEHALEM is an x86-64 core; upstream OpenBLAS has `kernel/x86_64/KERNEL.NEHALEM` and no `kernel/arm64/KERNEL.NEHALEM`. The port's own ARMV8 default (`deps/ports/openblas/cmake-project-include.cmake:39-40`) can never fire, because the block short-circuits at `:21` on `NOT "${TARGET}" STREQUAL ""`.

This is the first vcpkg command Task 4 runs, so it blocks everything.

**Second, larger issue in the same port.** `deps/vcpkg.json` requests `openblas` with `features: ["dynamic-arch"]`, so `DYNAMIC_ARCH=ON`. Upstream `cmake/arch.cmake` at v0.3.33, GNU branch:

```cmake
if (${CMAKE_C_COMPILER_VERSION} VERSION_GREATER_EQUAL 14) # SME ACLE supported in GCC >= 14
  set(DYNAMIC_CORE ${DYNAMIC_CORE} ARMV9SME)
endif()
```

GCC 16 clears that, so an arm64 build would compile roughly 14 dynamic cores including ARMV9SME, with `-march=armv9-a+sme` and raw SME assembly. This repo already knows that core is trouble: `deps/ports/openblas/android-exclude-sme.diff` exists to drop `ARMV9SME VORTEXM4`, but it patches only the **Clang** branch. The GNU branch this container uses is untouched.

**Resolution taken during execution: left alone, deliberately.** `DYNAMIC_LIST` was the obvious lever (`arch.cmake` honours it: `if (DYNAMIC_LIST) set(DYNAMIC_CORE ARMV8 ${DYNAMIC_LIST})`), but it cannot be delivered through this portfile. Its value is a semicolon-separated CMake list, and the portfile expands options unquoted (`${OPTIONS}`), which splits on semicolons. Verified: both `"-DL=A\;B"` and `"-DL=A\\;B"` still arrive as three separate arguments after the intermediate `set()` expansion. Carrying it would need a source patch or restructuring the configure call.

That is not worth pre-empting, because the feedback loop is short: OpenBLAS is the **first** vcpkg package Task 4 Step 5 builds, so an SME failure surfaces in minutes, not hours. If it does fail, the remedy is a patch in the `PATCHES` list of `portfile.cmake:8-15` gating `ARMV9SME` off upstream's GNU branch, mirroring the existing `android-exclude-sme.diff` which does exactly that for the Clang branch. Recorded in Risks.

Fixing `-DTARGET` alone does **not** address SME; it is a separate, unresolved risk being accepted with a known remedy.

### Task 3: Dual-arch toolchain stage

Both arches must end with a working GCC 16 on `/opt/gcc/bin` and CMake 4.4.3 on `/opt/cmake/bin`, so the single `ENV PATH=` line and every later stage stay arch-agnostic. Compiler Explorer publishes x86-64 only (`opt-arm64/gcc-16.2.0.tar.xz` returns 404), so arm64 installs the PPA package and symlinks it into the same layout.

`check-toolchain.sh` runs inside this stage and hardcodes `-march=x86-64-v2` plus an `ld-linux-x86-64.so.2` assertion. Both fail on arm64, so they are fixed here; the stage cannot build otherwise.

**Durability asymmetry, worth stating in the docs.** amd64 is pinned by SHA256 against an immutable S3 object. arm64 is pinned by an apt version string in a PPA, and PPAs garbage-collect superseded binaries. When `ubuntu-toolchain-r/test` publishes its next GCC 16 snapshot, `gcc-16=16-20260315-1ubuntu1~22~ppa1` will start failing with "Version not found" and the arm64 image becomes unbuildable with no code change on our side. `GCC_ARM64_APT_VERSION` is the single place to bump. Expect to do so periodically.

Verified while planning, so do not re-litigate: the PPA pin's version-sensitive dependencies are all `(= ${binary:Version})`, so pinning two packages is safe; `libgcc-16-dev` ships `libgcc.a`, `libgomp.a` and `libasan.a` and `libstdc++-16-dev` ships `libstdc++.a`, so the static link flags resolve; `software-properties-common` hard-depends on `gpg`. That is necessary but **not sufficient**: `add-apt-repository` imports the PPA key via `gpg --import`, which needs `gpg-agent`, and `gpg` only *Recommends* it, so `--no-install-recommends` strips it. Observed failure: `gpg: error running '/usr/bin/gpg-agent': probably not installed` followed by `ShortcutException ... returned non-zero exit status 2`. `gpg-agent` is therefore installed explicitly. No `ld.so.conf.d` entry is needed on arm64, because apt installs `libstdc++6` into the default search path and runs `ldconfig` via dpkg triggers, whereas the amd64 tarball hides it under `/opt/gcc/lib64`.

- [ ] **Step 1: Replace the GCC acquisition block**

Match on content: the block beginning `# Compiler Explorer's Ubuntu 22.04 build.` and ending `&& rm /tmp/gcc.tar.xz`. Replace it entirely with:

```dockerfile
# Compiler Explorer's Ubuntu 22.04 build. Keep this digest when mirroring it.
# Compiler Explorer publishes x86-64 only, so arm64 takes GCC 16 from the
# ubuntu-toolchain-r PPA and symlinks it into the same /opt/gcc layout. Both
# arches are GCC 16; the point releases differ and that is deliberate.
ARG GCC_VERSION=16.2.0
ARG GCC_SHA256=7bffbfc6b2eb997a7a6e3cbd013372b41de5746850ded8b6453f9820e5678828
ARG GCC_ARM64_APT_VERSION=16-20260315-1ubuntu1~22~ppa1
ARG TARGETARCH
RUN set -eux; \
    : "${TARGETARCH:=$(dpkg --print-architecture)}"; \
    if [ "${TARGETARCH}" = "arm64" ]; then \
      apt-get update; \
      apt-get install -y --no-install-recommends software-properties-common gpg-agent; \
      add-apt-repository -y ppa:ubuntu-toolchain-r/test; \
      apt-get update; \
      apt-get install -y --no-install-recommends \
        "gcc-16=${GCC_ARM64_APT_VERSION}" "g++-16=${GCC_ARM64_APT_VERSION}"; \
      mkdir -p /opt/gcc/bin; \
      for t in gcc g++ gcc-ar gcc-nm gcc-ranlib gcov; do \
        ln -s "/usr/bin/${t}-16" "/opt/gcc/bin/${t}"; \
      done; \
      rm -rf /var/lib/apt/lists/*; \
    else \
      curl -fL --retry 3 \
        "https://s3.amazonaws.com/compiler-explorer/opt/gcc-${GCC_VERSION}.tar.xz" \
        -o /tmp/gcc.tar.xz; \
      echo "${GCC_SHA256}  /tmp/gcc.tar.xz" | sha256sum -c -; \
      tar -xJf /tmp/gcc.tar.xz -C /opt; \
      ln -s "gcc-${GCC_VERSION}" /opt/gcc; \
      echo /opt/gcc/lib64 > /etc/ld.so.conf.d/luxir-gcc.conf; \
      ldconfig; \
      rm /tmp/gcc.tar.xz; \
```

### Task 7: Make the codec compile and be correct on aarch64

- [ ] **Step 1: Write the failing test**

Add to `test/basic_tests/PForTest.cpp`, immediately after `TEST_F(PForTest, pfordBaseCarry)`:

```cpp
// The T4 docid path stores gaps transposed across 4 lanes of 32 and un-transposes
// them on decode (t4Delta / t4InverseDelta in Codec.cpp).  t4Delta is
// unconditionally scalar while t4InverseDelta is architecture-dependent, so this
// round trip compares two different implementations rather than one against
// itself.  Uniform and strictly-distinguishable inputs make a lane permutation
// show up as a mismatch instead of coincidentally matching.
TEST_F(PForTest, pfordT4TransposeExactness) {
  LuxirPFORd fp;

  for (uint32_t step : {1u, 2u, 3u, 1u << 16, 1u << 24}) {
    std::vector<uint32_t> data(BLK);
    uint32_t acc = 0;
    for (auto& v : data) {
      acc += step;
      v = acc;
    }
    ASSERT_EQ(roundtrip(fp, data), data) << "uniform step " << step;
  }

  // Lane boundaries at 0/32/64/96: a large jump exactly on a boundary stresses
  // the per-lane base offsets that the un-transpose adds back.
  std::vector<uint32_t> steps(BLK);
  uint32_t acc = 0;
  for (uint32_t i = 0; i < BLK; ++i) {
    acc += (i % 32 == 0) ? 1000000u : 1u;
    steps[i] = acc;
  }
  ASSERT_EQ(roundtrip(fp, steps), steps) << "lane-boundary jumps";

  // The cases above all produce a residual matrix whose four lane rows are
  // identical, so they detect output-side permutations but not input-side ones.
  // Lane j owns docids [32j, 32j+32), so deriving the gap from both i/32 and
  // i%32 makes every lane's residual row distinct and distinct within itself.
  // Without this, an input-lane reversal survives most of this test.
  std::vector<uint32_t> laneDistinct(BLK);
  acc = 0;
  for (uint32_t i = 0; i < BLK; ++i) {
    const uint32_t lane = i / 32;
    acc += 1 + lane * 1000 + (i % 32) * (lane + 1);
    laneDistinct[i] = acc;
  }
  ASSERT_EQ(roundtrip(fp, laneDistinct), laneDistinct) << "per-lane distinct residuals";

  // Deterministic pseudo-random gaps, including zeros (repeated docids are
  // allowed here, per pfordRoundTrip).
  std::vector<uint32_t> mixed(BLK);
  uint32_t state = 12345u;
  acc = 0;
  for (uint32_t i = 0; i < BLK; ++i) {
    state = state * 1103515245u + 12345u;
    acc += (state >> 16) % 37u;
    mixed[i] = acc;
  }
  ASSERT_EQ(roundtrip(fp, mixed), mixed) << "mixed pseudo-random gaps";
}
```

The last two shapes matter. A mutation test showed that with only uniform-step and ramp inputs, an input-side lane reversal was caught by just one of seven assertions, because a uniform gap makes all four lanes' residual rows identical. `LuxirPFORd` has no ordering precondition beyond `inSz == BLOCK_SIZE`, and zero gaps are explicitly allowed (`PForTest.cpp:332`), so all of these inputs are valid.

The scalar `t4InverseDelta` supplied in Step 4 was verified during planning against `t4Delta` over 20,000 randomized trials plus these edge shapes. Do not improvise a different implementation; the transposed layout is the on-disk docs format, so a subtly different un-transpose yields silently wrong docids on ARM only.

```cpp
void t4InverseDelta(uint32_t* p, uint32_t base) {
#if defined(__x86_64__) || defined(__SSE2__)
  const __m128i* in = reinterpret_cast<const __m128i*>(p);
  __m128i rows[T4_ROWS];
  __m128i acc = _mm_setzero_si128();
  for (uint32_t m = 0; m < T4_ROWS; ++m) {   // acc.lane j = doc[32j+m] - laneBase[j]
    acc = _mm_add_epi32(acc, _mm_loadu_si128(in + m));
    rows[m] = acc;
  }
  // laneBase[j] = base + sum of lane totals below j; lane totals are the last row.
  uint32_t total[T4_LANES];
  _mm_storeu_si128(reinterpret_cast<__m128i*>(total), rows[T4_ROWS - 1]);
  uint32_t off[T4_LANES];
  off[0] = base;
  for (uint32_t j = 1; j < T4_LANES; ++j) off[j] = off[j - 1] + total[j - 1];
  const __m128i offv = _mm_loadu_si128(reinterpret_cast<const __m128i*>(off));
  // Add the lane base and un-transpose to natural order.  Each iteration adds the
  // base to 4 rows, then a 4x4 lane transpose turns those rows (lane-major) into
  // 4 vectors of consecutive rows per lane -- lane j's rows [mb, mb+4) land
  // contiguously at p[32j + mb], reconstructing ascending docids.
  for (uint32_t mb = 0; mb < T4_ROWS; mb += 4) {
    const __m128i r0 = _mm_add_epi32(rows[mb + 0], offv);
    const __m128i r1 = _mm_add_epi32(rows[mb + 1], offv);
    const __m128i r2 = _mm_add_epi32(rows[mb + 2], offv);
    const __m128i r3 = _mm_add_epi32(rows[mb + 3], offv);
    const __m128i t0 = _mm_unpacklo_epi32(r0, r1);
    const __m128i t1 = _mm_unpackhi_epi32(r0, r1);
    const __m128i t2 = _mm_unpacklo_epi32(r2, r3);
    const __m128i t3 = _mm_unpackhi_epi32(r2, r3);
    __m128i* op = reinterpret_cast<__m128i*>(p + mb);
    _mm_storeu_si128(op + 0 * (T4_ROWS / 4), _mm_unpacklo_epi64(t0, t2));  // lane 0
    _mm_storeu_si128(op + 1 * (T4_ROWS / 4), _mm_unpackhi_epi64(t0, t2));  // lane 1
    _mm_storeu_si128(op + 2 * (T4_ROWS / 4), _mm_unpacklo_epi64(t1, t3));  // lane 2
    _mm_storeu_si128(op + 3 * (T4_ROWS / 4), _mm_unpackhi_epi64(t1, t3));  // lane 3
  }
#else
  // Portable equivalent. FastPFOR's NEON shim has no _mm_unpack{lo,hi}_epi{32,64},
  // and the un-transpose is a plain 4x4 lane transpose, so express it directly.
  // Every row is read before any is written back, as above.
  uint32_t rows[T4_ROWS][T4_LANES];
  uint32_t acc[T4_LANES] = {0, 0, 0, 0};
  for (uint32_t m = 0; m < T4_ROWS; ++m) {
    for (uint32_t j = 0; j < T4_LANES; ++j) {
      acc[j] += p[T4_LANES * m + j];
      rows[m][j] = acc[j];
    }
  }
  uint32_t off[T4_LANES];
  off[0] = base;
  for (uint32_t j = 1; j < T4_LANES; ++j) {
    off[j] = off[j - 1] + rows[T4_ROWS - 1][j - 1];
  }
  for (uint32_t j = 0; j < T4_LANES; ++j) {
    for (uint32_t m = 0; m < T4_ROWS; ++m) {
      p[T4_ROWS * j + m] = rows[m][j] + off[j];
    }
  }
#endif
}
```

The `uint32_t` arithmetic wraps exactly as `_mm_add_epi32` does, so the two branches agree on overflow as well.

### Task 8: Commit a SIMD-vs-scalar byte oracle for the bit-packing kernels

Every existing codec test round-trips through the same kernel in both directions, so a symmetric NEON bug would pass all of them. `PForTest.vectorizedEncoderMatchesScalarBytes` does not close this: its "scalar" reference calls `FastPForLib::simdpack` at `PForTest.cpp:107`, and its own comment at `:81-82` says the bit-packing calls are "intentionally the production ones".

`deps/FastPFOR/src/bitpacking.cpp` contains zero SIMD, so its `fastpackwithoutmask` / `fastunpack` are a true cross-implementation oracle. The SIMD kernels pack four interleaved lanes of 32 values; output word `w*4 + lane` equals scalar word `w` of that lane's deinterleaved sequence.

This was run during planning on arm64 for all 32 bit widths against both production kernel families (`usimdpackwithoutmask`/`usimdunpack` and `simdpack`/`simdunpack`), and all agreed byte-for-byte. Committing it converts that one-off result into a permanent guard that also runs on x86.

```cpp
// Copyright 2020-2026 Yonik Seeley and Luxir contributors
// SPDX-License-Identifier: Apache-2.0

#include <gtest/gtest.h>

#include <cstdint>
#include <cstring>
#include <random>
#include <vector>

#include "luxir/codec/Codec.h"  // __m128i for the current target
#include "FastPFOR/headers/bitpackinghelpers.h"
#include "FastPFOR/headers/simdbitpacking.h"
#include "FastPFOR/headers/usimdbitpacking.h"

namespace {

// bitpacking.cpp contains no SIMD, so fastpackwithoutmask is identical on every
// target. The SIMD kernels pack 4 interleaved lanes of 32; output word
// w*4 + lane equals scalar word w of that lane's deinterleaved sequence.
// `masking` picks the scalar counterpart: fastpack masks each value to `bits`,
// fastpackwithoutmask assumes the caller already did. The SIMD kernels split the
// same way (simdpack masks, usimdpackwithoutmask does not), and the mask is a
// real NEON operation, so both need covering.
std::vector<uint32_t> scalarPackInterleaved(const uint32_t* in, uint32_t bits,
                                            bool masking) {
  std::vector<uint32_t> out(4 * bits, 0u);
  for (uint32_t lane = 0; lane < 4; ++lane) {
    uint32_t laneIn[32], laneOut[32];
    for (uint32_t j = 0; j < 32; ++j) laneIn[j] = in[j * 4 + lane];
    std::memset(laneOut, 0, sizeof laneOut);
    if (masking) {
      FastPForLib::fastpack(laneIn, laneOut, bits);
    } else {
      FastPForLib::fastpackwithoutmask(laneIn, laneOut, bits);
    }
    for (uint32_t w = 0; w < bits; ++w) out[w * 4 + lane] = laneOut[w];
  }
  return out;
}

std::vector<uint32_t> unmaskedBlock(std::mt19937& rng) {
  std::vector<uint32_t> in(128);
  for (uint32_t i = 0; i < 128; ++i) in[i] = rng();
  return in;
}

std::vector<uint32_t> randomBlock(std::mt19937& rng, uint32_t bits) {
  const uint32_t mask = (bits == 32) ? 0xFFFFFFFFu : ((1u << bits) - 1u);
  std::vector<uint32_t> in(128);
  for (uint32_t i = 0; i < 128; ++i) in[i] = rng() & mask;
  return in;
}

}  // namespace

TEST(FastPForKernelTest, usimdPackMatchesScalarBytes) {
  std::mt19937 rng(4242);
  for (uint32_t bits = 1; bits <= 32; ++bits) {
    const std::vector<uint32_t> in = randomBlock(rng, bits);
    std::vector<uint32_t> simd(4 * bits + 8, 0u);
    FastPForLib::usimdpackwithoutmask(in.data(), (__m128i*) simd.data(), bits);
    const std::vector<uint32_t> scalar = scalarPackInterleaved(in.data(), bits, /*masking=*/false);
    EXPECT_EQ(0, std::memcmp(simd.data(), scalar.data(),
                             4 * bits * sizeof(uint32_t)))
        << "usimdpackwithoutmask diverges from scalar at bits=" << bits;
  }
}

TEST(FastPForKernelTest, simdPackMatchesScalarBytes) {
  std::mt19937 rng(4243);
  for (uint32_t bits = 1; bits <= 32; ++bits) {
    const std::vector<uint32_t> in = randomBlock(rng, bits);
    std::vector<uint32_t> simd(4 * bits + 8, 0u);
    FastPForLib::simdpack(in.data(), (__m128i*) simd.data(), bits);
    const std::vector<uint32_t> scalar = scalarPackInterleaved(in.data(), bits, /*masking=*/false);
    EXPECT_EQ(0, std::memcmp(simd.data(), scalar.data(),
                             4 * bits * sizeof(uint32_t)))
        << "simdpack diverges from scalar at bits=" << bits;
  }
}

TEST(FastPForKernelTest, usimdUnpackRecoversScalarPackedBytes) {
  std::mt19937 rng(4244);
  for (uint32_t bits = 1; bits <= 32; ++bits) {
    const std::vector<uint32_t> in = randomBlock(rng, bits);
    std::vector<uint32_t> scalar = scalarPackInterleaved(in.data(), bits, /*masking=*/false);
    scalar.resize(4 * bits + 8, 0u);
    std::vector<uint32_t> back(128, 0u);
    FastPForLib::usimdunpack((const __m128i*) scalar.data(), back.data(), bits);
    EXPECT_EQ(in, back)
        << "usimdunpack diverges from scalar layout at bits=" << bits;
  }
}
TEST(FastPForKernelTest, simdPackMasksLikeScalarFastpack) {
  // simdpack masks each value to `bits` before packing; Codec.cpp:269-271 relies
  // on that ("exception values keep only their low bestb bits here"). Feeding it
  // pre-masked input never exercises the mask, so use unmasked input and compare
  // against the masking scalar. Measured: with unmasked input simdpack differs
  // from fastpackwithoutmask at 31/31 widths and matches fastpack at 31/31.
  std::mt19937 rng(4245);
  for (uint32_t bits = 1; bits <= 31; ++bits) {
    const std::vector<uint32_t> in = unmaskedBlock(rng);
    std::vector<uint32_t> simd(4 * bits + 8, 0u);
    FastPForLib::simdpack(in.data(), (__m128i*) simd.data(), bits);
    const std::vector<uint32_t> scalar =
        scalarPackInterleaved(in.data(), bits, /*masking=*/true);
    EXPECT_EQ(0, std::memcmp(simd.data(), scalar.data(),
                             4 * bits * sizeof(uint32_t)))
        << "simdpack's mask diverges from scalar at bits=" << bits;
  }
}

TEST(FastPForKernelTest, simdUnpackRecoversScalarPackedBytes) {
  // simdunpack is the kernel on the production decode path (Codec.cpp:298);
  // usimdunpack (covered above) is a different entry point.
  std::mt19937 rng(4246);
  for (uint32_t bits = 1; bits <= 32; ++bits) {
    const std::vector<uint32_t> in = randomBlock(rng, bits);
    std::vector<uint32_t> scalar =
        scalarPackInterleaved(in.data(), bits, /*masking=*/false);
    scalar.resize(4 * bits + 8, 0u);
    std::vector<uint32_t> back(128, 0u);
    FastPForLib::simdunpack((const __m128i*) scalar.data(), back.data(), bits);
    EXPECT_EQ(in, back)
        << "simdunpack diverges from scalar layout at bits=" << bits;
  }
}
```

## Risks

- **OpenBLAS ARMV9SME.** `dynamic-arch` on GCC >= 14 adds an `ARMV9SME` core built with `-march=armv9-a+sme` and raw SME assembly. The repo's `android-exclude-sme.diff` already drops it, but only on upstream's Clang branch. Jammy's binutils 2.38 does document `sme` support, so this may simply work. If it does not, add a patch gating `ARMV9SME` off the GNU branch to `portfile.cmake`'s `PATCHES` list. Surfaces early: OpenBLAS is the first package built.
- **FAISS on aarch64.** It carries x86 SIMD paths and its CMake normally selects a generic build on ARM. `test/basic_tests/VectorIndexBuilderTest.cpp` and `IndexReaderAuxTest.cpp` exercise it inside `luxir_test`, so Task 9 Step 2 gates correctness and Step 6 gates the vector benchmarks. A failure here is a finding to report, not a dependency to drop.
- **Other vcpkg ports.** gRPC, protobuf and Boost all support arm64 upstream, but this baseline has not been exercised on it in this repo. Task 4 Step 5 is where that surfaces.
- **GCC point-release asymmetry.** amd64 gets 16.2.0, arm64 gets the 20260315 snapshot. `GCC_ARM64_APT_VERSION` is the single place to move if a snapshot bug appears.
- **New `-Werror` failures.** Debug builds treat warnings as errors and GCC 16 on a new target will likely produce some. Budget for fixing them in Task 7; if they are numerous, enumerate them with a `container-arm64-release` build first, where they are warnings.
- **`DOCKER_DEFAULT_PLATFORM`.** If the environment sets it to `linux/amd64` (common on Apple Silicon), `TARGETARCH` becomes `amd64` and all of Phase A silently builds the x86 path under emulation, with `check-toolchain.sh` agreeing because it reads `uname -m`. Task 3 Step 5 asserts `uname -m` is `aarch64` to catch this.
- **arm64 toolchain pin is less durable than amd64's.** amd64 is a SHA256 over an immutable S3 object; arm64 is an apt version in a PPA, and PPAs garbage-collect superseded binaries. Expect to bump `GCC_ARM64_APT_VERSION` periodically; the image becomes unbuildable with no code change when the snapshot is superseded.
- **Emulated amd64 verification.** Slow on Apple Silicon and may be impractical. Tasks 9 Steps 4 and 5 both depend on it. Report honestly if skipped.
- **`deps/make_deps.sh` is still x86-only.** It hardcodes `x64-linux-luxir-native` / `-native-asan` and probes `-march=native`, so the native `gcc-*` presets remain x86-only after this port. Out of scope here; worth a follow-up if native arm64 development outside the container is ever wanted.
- **No build CI exists.** `.github/workflows/` has only `proto-docs.yml` and `site-docs.yml`, so nothing prevents a future unguarded `#include <immintrin.h>` from re-breaking aarch64. The cheapest guard is a cross-compile syntax check (`aarch64-linux-gnu-g++ -fsyntax-only` over the arch-guarded headers with `-Isrc -Ideps`), which runs in seconds and needs no container. Deliberately not included here because adding CI is a separate decision; raise it after this lands.
